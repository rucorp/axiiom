tbank-mock — мок-стенд Т-Банк: эквайринг, Мультирасчёты и E2C ​

Локальный тестовый банк с HTTP-контрактами /v2/*, E2C-выплатами, проверкой счёта, рекуррентными платежами, СБП/QR, партнёрской регистрацией, Token-подписью, платёжной формой, подписанными нотификациями и админ-консолью. Профиль plain (по умолчанию) моделирует обычный эквайринг; multisplit добавляет обязательные поля и балансовые правила Мультирасчётов. Исследовательская база — конспекты провайдеров в приватном репозитории mock-services-docs; публичный источник — официальная документация Т-Банка.

Node.js >= 18; внешние npm-зависимости не нужны. Сервер использует общий модуль packages/core для HTTP, персистентности, sandbox и защитных helpers.

Зачем ​

Реальный тестовый контур банка недоступен без договора + IP-whitelist и требует запросов с боевого терминала (см. RES-007 §1). Мок даёт управляемые сценарии: успех/frictionless, 3DS-challenge, недостаточно средств, отказы, частичные возвраты, дубли и ретраи нотификаций, авто-подтверждение холда.

Запуск ​

bash
docker compose up -d tbank-mock          # порт 3100
# или голым node
MOCK_TERMINAL_KEY=TBANKMOCKTEST MOCK_TERMINAL_PASSWORD=mockpass123 node services/tbank-mock/server.js

Самотест (48 сценариев: контракты эквайринга/Мультирасчётов/E2C, TerminalKey и CSRF, песочницы, подписи и webhook-ретраи; все процессы слушают ephemeral-порты):

bash
npm run test:tbank

Подключение своего приложения к моку ​

Приложение ходит в мок как в банк: укажите в конфигурации базовый URL мока и креды стенда (внутри docker-сети сервис доступен как http://tbank-mock:3100):

env
TBANK_API_URL=http://tbank-mock:3100/v2   # или http://localhost:3100/v2 с хоста
TBANK_TERMINAL_KEY=TBANKMOCKTEST          # те же ключи видит мок
TBANK_TERMINAL_PASSWORD=mockpass123
TBANK_NOTIFICATION_URL=https://<ваш домен>/api/v1/payments/tbank/webhook

Клиент не меняется: запросы подписываются Token (sha256) как в бою, нотификации приходят снаружи и проверяются по-настоящему. Пошаговая цепочка curl — в гайде «за 10 минут».

Правила, история срабатываний и журнал /admin/journal принадлежат текущей песочнице (#52): другие песочницы их не видят и не очищают, POST /mock/reset действует только на целевую песочницу. Лимиты: до 200 правил на песочницу и до 8 KiB на правило (превышение — HTTP 400 с code rule_cap_exceeded/rule_too_large).

acqapi: OAuth и регистрация точки ​

POST /oauth/token принимает только фактический Basic-клиент: по умолчанию partner:partner, либо MOCK_ACQAPI_CLIENT_ID + MOCK_ACQAPI_CLIENT_SECRET. Поддерживаются grant_type=password (документированный контур) и client_credentials; ответ выдаёт случайный opaque Bearer со scope=partner и TTL 3600 секунд (переопределяется MOCK_ACQAPI_TOKEN_TTL_MS). Токен проверяется на POST/GET/PATCH /sm-register/register*; произвольная строка Bearer, истёкший токен и запрос без Authorization возвращают 401.

Регистрация требует полную JSON-схему из документации Т-Банка: shopArticleId (латиница/цифры/._-, до 32 символов), billingDescriptor, fullName, name, inn, kpp, ogrn, непустые addresses[] (type, zip, country ISO-3, city, street), ceo.phone/ceo.citizenship, founders.individuals[], email, siteUrl, bankAccount (account, korAccount, bankName, bik, details) и boolean nonResident. kbk и oktmo при передаче обязательны парой; mcc допускается как 4-значный override. shopArticleId без генерации маппится в shopCode, который используется как PartnerId в e2c-выплате. Валидация выполняется до записи state.

Терминал проверяется вместе с подписью во всех payout-операциях, включая Payment, GetState, GetSbpMembers и CancelPayment; неверный или отсутствующий TerminalKey возвращает provider-shaped ошибку до поиска/изменения выплаты. MOCK_ADMIN_TOKEN ограничивает консоль, а native POST-формы передают CSRF-токен и сохраняют query-token админки и owner-token owned-песочницы при отправке/redirect.

Нотификации: подписанный POST (Token покрывает SpAccumulationId) на NotificationURL из Init; ответ должен быть ровно OK, иначе ретраи (MOCK_RETRY_MS × MOCK_MAX_ATTEMPTS, по умолчанию 60 с × 24 — как у банка «раз в час в течение суток», но сжато для тестов). Нотифицируемые статусы: AUTHORIZED, CONFIRMED, REVERSED, PARTIAL_REVERSED, REFUNDED, PARTIAL_REFUNDED, REJECTED.

Надёжность очереди (после аудита 2026-10-08): одна нотификация = максимум один POST «в полёте» (ретраи не накладываются), доставленные записи помечаются done и не переотправляются, а недоставленные переживают рестарт с MOCK_STATE_FILE и продолжают ретраиться.

Песочницы и hosted tenancy (RFC-001, A-21) ​

Каждый запрос разрешает свою песочницу один раз и дальше видит только её состояние, креды и персистентность: параллельные A/B-запросы не смешиваются между await, а запрос без селектора всегда попадает в default, а не остаётся в предыдущей песочнице. Селектор: X-Mock-Sandbox: <id> → ?sandbox=<id> → поддомен <id>.<MOCK_SANDBOX_HOST_SUFFIX> (если суффикс задан). PaymentURL платежа в именованной песочнице уже содержит ?sandbox=<id>.

РежимВключаетсяПоведение
namespacesдефолт self-hosted; MOCK_TENANCY=namespacesX-Mock-Sandbox создаёт изолированное пространство имён для параллельных CI-воркеров; креды и управляющие токены — общие
ownedMOCK_HOSTED=1 по умолчанию; MOCK_TENANCY=owned (legacy 1/on/true/yes)у каждой песочницы свои креды и owner-token (показывается один раз); знание id без owner-token доступа не даёт (401), неизвестный id — 404, истёкший — 410
offMOCK_TENANCY=off (legacy 0/false/no)одна общая песочница default; селектор игнорируется

API (в owned — с owner-token; в namespaces те же маршруты управляют пространствами имён без owner-token):

ЗапросЧто делает
POST /sandboxesсоздать песочницу: id, url, creds (свой TerminalKey/TerminalPassword) и ownerToken — показывается один раз
GET /sandboxes (алиас GET /mock/sandboxes)список: владельцу — своя песочница, оператору (MOCK_OPERATOR_TOKEN) — все
DELETE /sandboxes?sandbox=<id>удалить песочницу вместе с состоянием (владелец или оператор)
GET /sandboxes/meсвоя песочница: состояние, креды, TTL, расход квоты; POST /sandboxes/me/reset, POST /sandboxes/me/reset-creds, DELETE /sandboxes/me

Owner-token принимается в Authorization: Bearer, X-Sandbox-Token или ?sandbox_token=. Персистентность: реестр песочниц пишется атомарно и поштучно — по файлу <MOCK_STATE_FILE>.sandboxes.records/<id>.json на песочницу (хэши owner-токенов + снимки состояния; мутация переписывает только свою песочницу, PD-02), а default всегда восстанавливается только из MOCK_STATE_FILE — состояние именованной песочницы не может быть выдано за default (F-14). Просроченные песочницы удаляет sweep-воркер; квота документов (MOCK_SANDBOX_MAX_DOCUMENTS) проверяется до создания платежа/сделки/выплаты и отвечает ошибкой 7 с подсказкой.

Границы симуляции ​

  • Это локальный mock server, а не тестовый/боевой контур банка: платежи, выплаты, СБП и account verification имеют только синтетическое состояние; реальные карты, ключи и персональные данные использовать нельзя.
  • Поддерживаются только маршруты и конечные автоматы, перечисленные выше. Не реализованные методы возвращают provider-shaped ошибку «501»; наличие тестового ответа не означает сертификацию или полную эквивалентность API банка.
  • Список SBP-участников и карточные сценарии статические. Состояние хранится в памяти, если не задан MOCK_STATE_FILE; никакие операции не проводят реальные денежные средства.
  • Перед изменением production-интеграции сверяйте поля и статусы с актуальной документацией Т-Банка и согласованным профилем (plain/multisplit).

Байтовые квоты состояния (PD-02) ​

EnvДефолтНазначение
MOCK_SANDBOX_MAX_STATE_BYTESпусто: 8388608 (8 МиБ) при maxDocuments > 0, иначе без лимитабайты JSON одной песочницы; 0 выключает

Значения задаются в целых байтах. Пусто сохраняет дефолты. Квота per-sandbox не ограничивает память контейнера; общий бюджет меньше mem_limit: 128m, но не равен RSS. Превышение глобального бюджета на записи или байтовых квот при импорте /mock/state → HTTP 400, errorCode: 400, kind: 'bytes', code: sandbox_state_budget_exceeded / sandbox_state_quota_exceeded, с откатом отклонённого состояния. Правила/история/журнал остаются volatile. Подробности и границы — документация ядра.
