sber-mock — Сбербанк Ecom REST v1.1.11.1 ​

Реализован по официальной документации Сбербанк Ecom REST. Это новый Ecom JSON API, не legacy Secure Payments: POST /ecomm/gw/partner/api/v1/*.do, userName/password в теле каждого вызова, регистрация → formUrl → hosted-форма/ACS → серверная сверка getOrderStatusExtended.do.

Быстрый старт ​

bash
npm run start:sber          # http://localhost:3105
# или общий локальный стенд:
docker compose up -d sber-mock

Node ≥ 18, zero npm dependencies. Синтетические дефолты — SBERMOCKTEST / mockpass123; это не тестовые креды банка. Фактические env значения при запуске скрыты в логах. Банк выдаёт реальные тестовые userName/password подключённому merchant отдельно; не помещайте их в код, тесты, fixtures или общий compose-файл.

paymentOrder.do не реализован: это прямой карточный server-to-server флоу, доступность которого требует merchant-разрешения. SberPay/SBP Sandbox, СБП и orderBundle также не входят в адаптер.

REST-тело — JSON UTF-8 (Content-Type: application/json), валюта только RUB 643, суммы — целые копейки. Merchant orderNumber уникален в рамках песочницы; повтор не переигрывает исходный запрос. По умолчанию заказ живёт 1200 секунд и имеет не более трёх попыток оплаты. Детальные примеры регистрации, оплаты, deposit/refund и callback находятся в гайде интегратора.

errorCode=0 означает, что обработан конкретный REST-вызов, а не то, что платёж успешен. Источник истины по заказу — числовой orderStatus 0…6; actionCode/actionCodeDescription описывают результат/причину операции и не подменяют состояние заказа. Состояния и переходы — по официальной документации протокола.

Callback Ecom ​

Исходящее Ecom callback — HTTP POST JSON без подписи или checksum, с mdOrder, orderNumber, operation, числовым status (1/0) и опциональным additionalParams. Поддержанные операции: created, approved, deposited, reversed, refunded, declinedByTimeout. Только HTTP 200 считается ACK. По умолчанию очередь делает три попытки с интервалом 60 секунд; локальные виртуальные часы ускоряют retry. Для регистрации callback URL задаётся в dynamicCallbackUrl, либо глобально через MOCK_SBER_CALLBACK_URL.

Подписи/checksum в Ecom callback нет. Мок не использует и не эмулирует подпись legacy Secure Payments. Неподписанный callback — сигнал к повторной серверной сверке getOrderStatusExtended.do, а не доказательство успешной оплаты. В отсутствии callback URL очередь не создаётся.

Ошибки и протокольные оговорки ​

Ответы бизнес-ошибок моделируются как HTTP 200 + {errorCode,errorMessage}; field, hint и doc — диагностическое расширение мока. HTTP 400/404/405/413/ 415/500 применяется к транспортным/инфраструктурным ошибкам. Числа 1…6 и частные соответствия (дубликат, авторизация, неизвестный заказ, неверное состояние, сумма/валидация, системная ошибка) — [VERIFY]/[FORK]: локальный документация Ecom фиксирует envelope и отдельные описанные ошибки, но не полный merchant-каталог errorCode. Не используйте эти маппинги как обещание production-шлюза; перед точным контрактным тестом их нужно сверить с подключённым Ecom merchant.

orderStatus 0…6 документирован в reference для общего семейства Ecom/RBS. Повторяемые test-card action codes 101 и 116 — сценарии официальных тестовых карт. Всё прочее, где публичная Ecom-документация неполна, остаётся явным мок-форком, а не добавляется под видом подтверждённого протокола.

Сценарии, часы и диагностика ​

X-Mock-Scenario//mock/scenarios поддерживают fail, hang, latency, http-500, http-504, webhook-drop/no-callback и webhook-duplicate/callback-duplicate. REST chaos с abortStatus происходит до бизнес-операции. Карточные отказы выбираются официальными тестовыми пресетами. POST /mock/time принимает, например, {"advance":"+20m"} для истечения заказа или {"advance":"+60s"} для повторной доставки callback.

Сценарии, их история, журнал и состояние изолируются по X-Mock-Sandbox. Журнал redacts чувствительные поля; PAN не пишется в REST-журнал и не сохраняется в заказе — в заказе остаётся только маска first6**last4. В hosted-режиме SSRF-проверка исходящих callback включается по умолчанию; SSRF_BLOCKED — терминальный отказ без повтора.

Байтовые квоты состояния ​

EnvДефолтНазначение
MOCK_SANDBOX_MAX_STATE_BYTESпусто: 8388608 (8 МиБ) при maxDocuments > 0, иначе без лимитабайты JSON одной песочницы; 0 выключает
MOCK_SANDBOX_GLOBAL_MAX_STATE_BYTES67108864 (64 МиБ)сумма байт JSON всех песочниц рантайма, включая default; 0 выключает

Значения задаются в целых байтах. Пусто сохраняет дефолты. Квота per-sandbox не ограничивает память контейнера; общий бюджет меньше mem_limit: 128m, но не равен RSS. Превышение глобального бюджета на записи или байтовых квот при импорте /mock/state → HTTP 400, errorCode: 400, kind: 'bytes', code: sandbox_state_budget_exceeded / sandbox_state_quota_exceeded, с откатом отклонённого состояния. Правила/история/журнал остаются volatile. Подробности и границы — документация ядра.
