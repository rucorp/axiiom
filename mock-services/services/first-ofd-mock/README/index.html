first-ofd-mock — облачная касса OKassa (Первый ОФД) ​

Реализован по официальной документации OKassa API и тестового стенда Первого ОФД (по состоянию на 2026-10-11): тестовый контур external-api-farm.1-ofd-test.ru, getToken → Authorization: Bearer, асинхронная очередь заявок на чекPOST /api/external/queue/v1/transaction/{type} → requestId, статусы IN_PROGRESS/COMPLETED/ERROR.

Модель — асинхронная очередь заявок, а не синхронный вызов; операции записаны как INCOME, INCOME_RETURN, EXPENCE, EXPENCE_RETURN. Тег ATOL Online V5 из тестового swagger Первого ОФД (/api/external/possystem/v5/…) — отдельный API и вне области адаптера.

Быстрый старт ​

bash
npm run start:first-ofd    # http://localhost:3107
# или общий локальный стенд:
docker compose up -d first-ofd-mock

Node ≥ 18, zero npm dependencies. Синтетические дефолты — firstofdmocktest / 11111111-2222-4333-8444-555555555555; это не реквизиты Первого ОФД: публичных тестовых login/API-key UUID у провайдера нет, они выдаются в тестовом ЛК. Фактические env-значения при запуске скрыты в логах (<задан через env, скрыт>). Реальные тестовые креды не помещайте в код, тесты, fixtures или общий compose-файл.

Поддерживаемый поток OKassa ​

GET /api/external/receipts?from=&to=фискальные документы за период (фильтры transactionType, groupId, kkmRegId, page, pageSize)

Схема тела строго по типу заявки: receipt → ReceiptRequest, receiptCorrection → ReceiptCorrectionRequest (+ обязательный document.correctionCause), openShift/closeShift/currentStateReport → StateCommandRequest. Receipt-тело (document с operationType/items/ totalSum) в командах смены отклоняется — «универсальный» объект из схем разных провайдеров не собирается. Состав обязательных полей StateCommandRequest публично не раскрыт [VERIFY]: мок требует документированный requestMetadata.userGroup.

Авторизация и токен ​

POST /getToken принимает JSON с login и pass (API-ключ UUID из ЛК «Облачные кассы → Интеграции → Ключи к Кассовому API»). Успех — {token} + заголовки X-Mock-Token-TTL-Secs/X-Mock-Token-Expires-At; ошибки — invalid_credentials (401) или invalid_request (400). Дальше запросы несут Authorization: Bearer <token>.

Токен живёт 86400 секунд (24 часа) на виртуальных часах: POST /mock/time {"advance":"+25h"} делает прежний токен невалидным, новый getToken — снова рабочим. Повторная выдача по умолчанию не аннулирует прежний токен (документация об этом молчит — [VERIFY]); режим MOCK_FIRST_OFD_TOKEN_SINGLE=1 включает аннулирование, чтобы проверить и такое поведение.

Квирк примера PDF. Под заголовком успешного ответа getToken в PDF приведён объект error с кодом 0 и текстом «Неверный логин и пароль» (расхождение №4 документации): по HTTP 200 нельзя однозначно судить об успехе. Мок не угадывает семантику — дефолтный успех отдаёт только {token}, а документированный квирк воспроизводится сценарием getToken-error-quirk.

Очередь, статусы и деньги ​

POST transaction/{type} возвращает requestId — не финальный фискальный результат: заявка сначала IN_PROGRESS, затем COMPLETED или ERROR (в моке обработка занимает MOCK_FIRST_OFD_PROCESS_MS, по умолчанию 2000 мс виртуальных часов). Объект результата несёт requestId, transactionType, errorCode, errorType, details, payload; pending-поля равны null.

Ошибки двух слоёв сохраняются раздельно: errorType=API — слой API очереди, errorType=KKT — слой ККТ/фискального накопителя. Таблица значений публично не зафиксирована, поэтому каталоги KKT_ERROR_CODES/API_ERROR_CODES — явный [FORK] мока.

Денежные значения (price, totalSum, vatSums, ecashSums) — десятичные рубли (150.00), не копейки; внутри стенд считает в целых копейках. Операции INCOME/INCOME_RETURN/EXPENCE/EXPENCE_RETURN и ставки НДС включая VAT_22/VAT_22122 — как в схеме; написание EXPENCE мок не «исправляет», а вариант EXPENSE отклоняет с подсказкой. Правила сверки totalSum с позициями документация не описывает — это вне области, мок лишь предупреждает в логе.

Callback ​

Если в requestMetadata.callbackUrl передан URL (или задан MOCK_FIRST_OFD_CALLBACK_URL — fallback мока [FORK]), после обработки заявки уходит POST с JSON-телом результата плюс externalId/userGroup.

Публичная документация не закрепляет ни envelope, ни подпись, ни обязательный ACK, ни расписание повторов — мок не выдумывает HMAC/RSA: подписи нет вовсе. Тело уведомления, условие «любой 2xx = доставлено» и график повторов MOCK_FIRST_OFD_CALLBACK_RETRY_MS × MOCK_FIRST_OFD_CALLBACK_MAX_ATTEMPTS (дефолт 3 × 60 с) — локальная договорённость стенда [FORK], а не утверждение о протоколе Первого ОФД. Приёмник должен быть идемпотентным, результат подтверждается методом статуса. Расхождение по схеме URL (http:// в PDF против https:// в примерах) по умолчанию не разрешается в чью-то пользу: принимаются обе схемы, строгий HTTPS включается MOCK_FIRST_OFD_CALLBACK_HTTPS_ONLY=1. Приватный callbackUrl при MOCK_BLOCK_PRIVATE_WEBHOOKS даёт терминальный SSRF_BLOCKED без повторов.

Идемпотентность и externalId ​

externalId — внешний идентификатор вызывающей стороны. Правила дедупликации и срок хранения публично не подтверждены [VERIFY]. Мок фиксирует детерминированное поведение: повтор с тем же externalId в той же группе создаёт новую заявку со своим requestId (ответ помечается X-Mock-Duplicate-External-Id: 1), обе находятся через statuses. Для сверки сохраняйте выданный requestId — это ключ к статусу и фискальному документу.

Сценарии, часы и диагностика ​

X-Mock-Scenario//mock/scenarios поддерживают fail (HTTP 500 на вызове), hang, latency, http-500/http-504, kkt-error и api-error (завершение заявки ошибкой слоя ККТ/API), getToken-error-quirk, webhook-drop/ no-callback, webhook-duplicate/callback-duplicate. Естественные правила стенда возвращают SHIFT_ALREADY_OPEN/SHIFT_NOT_OPEN при повторном открытии/закрытии смены (правила ККТ-слоя документацией не описаны — [FORK]). POST /mock/time принимает {"advance":"+5s"} (обработка очереди), {"advance":"+25h"} (истечение токена) и {"advance":"+60s"} (retry callback). Сценарии, история, токены, журнал и состояние изолируются по X-Mock-Sandbox. Журнал redacts чувствительные поля; в hosted-режиме SSRF-проверка исходящих callback включена по умолчанию.

В owned-модели (MOCK_HOSTED=1) доступ к своей песочнице даёт owner-token (X-Sandbox-Token). Наблюдаемое ограничение стенда [VERIFY]: если в одном запросе есть и Authorization: Bearer <токен очереди>, и X-Sandbox-Token, ядро (RFC-001) читает owner-token из Authorization и отвечает 401 «знание ID не является доступом». Для локальных сценариев внутри одной песочницы используйте namespaces (self-hosted дефолт) или MOCK_TENANCY=off.

Значения задаются в целых байтах. Пусто сохраняет дефолты. Квота per-sandbox не ограничивает память контейнера; общий бюджет меньше mem_limit: 128m, но не равен RSS. Превышение глобального бюджета на записи или байтовых квот при импорте /mock/state → HTTP 400, errorCode: 400, kind: 'bytes', code: sandbox_state_budget_exceeded / sandbox_state_quota_exceeded, с откатом отклонённого состояния. Правила/история/журнал остаются volatile. Подробности и границы — документация ядра.
